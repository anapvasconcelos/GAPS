# Module 5 - Publishing

<!-- Survey2026 -- > <!-- MendezEtAl2020 -- > <!-- Montgomery2024 -->
Preparing an artifact for your own use is not the same as preparing it for others. Publishing requires assembling all components (data, code, documentation, licenses, and metadata) into a coherent, self-contained bundle that others can retrieve, install, and use independently. Without proper archival and citation practices, even well-prepared artifacts may disappear over time, preventing others from verifying, reusing, or building upon your work.

A good published artifact is self-explanatory without requiring access to the paper, and allows users to reproduce at least one key result, understand how results were generated, and extend or adapt the work for new purposes.

# Learning objectives

By the end of this module, you will be able to:

- Select appropriate repositories for artifact publication based on archival requirements.
- Assign licenses to software and non-software artifacts correctly.
- Prepare a self-contained artifact package ready for public release.
- Create and include citation metadata (PIDs, CITATION.cff) in your artifact.
- Write a Data Availability Statement (DAS) for different sharing scenarios.
- Handle restricted and sensitive data transparently at publication time.

# Where to publish artifacts

The rationale for avoiding cloud storage, GitHub, and institutional websites and the requirements for a valid archival platform were introduced in [Module 2 - Preparation](content/M2.md). This section provides the complete guidance for publication time.

## Recommended archival repositories

<!-- Montgomery2024 -- > <!-- Graziotin2019 -->
| Repository | Type | PID support | Notes |
|---|---|---|---|
| **Zenodo** | General purpose | DOI | ✅ Fully recommended. Free, supported by CERN and OpenAIRE. Supports versioning and GitHub integration. |
| **FigShare** | General purpose | DOI | ⚠️ Recommended with caution. Commercial platform, but content preservation supported through CLOCKSS. |
| **Dryad** | Data | DOI | ✅ Recommended for datasets. Supports versioning while preserving stable dataset identifiers. |
| **Software Heritage** | Source code | SWHID | ✅ Recommended for long-term source code preservation. Does not accept direct deposits. Archives code from public repositories such as GitHub and GitLab. |

The directory [re3data.org](https://www.re3data.org/) can help identify additional suitable repositories for specific disciplines or data types. <!-- SonjaEtAl2018 -->

> **Note:** Software Heritage provides persistent identification (SWHID) for source code, but DOIs remain more widely integrated into academic citation and indexing workflows. For this reason, many researchers combine Software Heritage for preservation with Zenodo for citable software releases.


## Repository selection criteria

When selecting a repository, verify that it supports: <!-- AdarEtAl2017 --> <!-- Montgomery2024 --> <!-- JORS -->

- Persistent identification (e.g., DOI, Handle, ARK, SWHIDs).
- Immutable releases: once published, content cannot be silently modified.
- Long-term preservation with a declared preservation policy.
- Public access without registration requirements.
- Metadata support for discoverability.
- Versioning: ability to publish new versions while maintaining old ones.
- Integration with development platforms (e.g., GitHub-to-Zenodo).

> **Tip:** Prefer repositories that allow anonymous access and do not require user registration, manual approval, or restrictive access controls to download the artifact. Avoid platforms that track user access or require individual download permissions. <!-- Survey2026 -->

## Recommended two-step workflow

> **Tip:** Separate active development from long-term archival. 

<!-- Survey2026 -- > <!-- ICSE2026 -- > <!-- MODELS2025 -->
1. **Develop on GitHub** (or similar): use for active development, collaboration, and version control throughout the research lifecycle.
2. **Archive a release on Zenodo** (or similar): create a stable, citable version at publication time.
3. **Cite the PID** in the paper.

Linking a GitHub release to Zenodo via the [GitHub-Zenodo integration](https://docs.github.com/en/repositories/archiving-a-github-repository/referencing-and-citing-content) is an accepted and recommended practice. A similar integration is available for [FigShare](https://knowledge.figshare.com/articles/item/how-to-connect-figshare-with-your-github-account). <!-- ICSE2026 --> <!-- MODELS2025 -->

> **Tip:** Provide URLs to both repositories (e.g., GitHub for the actively maintained version and Zenodo for the preserved version) so users know both exist and can access the appropriate one for their purpose. <!-- MODELS2025 -->

> **Note:** Supplementary material published in open archival repositories is independently archived and receives its own  persistent identifier and version record. Material published on personal or project webpages does not receive a PID, is volatile, and may disappear over time. When the paper has supplementary material intended for long-term accessibility, treat it as an artifact and archive it accordingly. <!-- ConfPub -->

# Preparing the artifact package

## What to include

An artifact package should contain everything necessary to understand and reproduce the study: <!-- Survey2026 --> <!-- ICSE2026 -->

- Raw data (when permitted).
- Processed data.
- Scripts and code for data collection, transformation, and analysis.
- Study protocols, instruments, and supporting materials.
- Tools and configurations.
- Sample outputs for comparison.
- Documentation (README, licenses, citation file).
- An explicit disclosure statement covering potential conflicts of interest, funding sources, limitations or constraints of the artifact, ethical considerations (e.g., data handling conditions), and a description of what is included and excluded from the shared materials and why.

> **Note:** Artifacts do not need to be complete to be valuable, they simply need to be relevant to the study and add value beyond the paper. Even the data behind a single figure can improve transparency significantly. <!-- ICSE2026 -->

## What to omit

Remove everything that increases complexity without adding value: <!-- Survey2026 -->

- Old versions of files, temporary or backup files.
- Unused scripts or data.
- Internal comments, TODOs, and personal notes.
- Materials not referenced in the paper.

> **Warning:** Do not release partial artifacts. Incomplete artifacts hinder reproducibility, fair comparison, and proper evaluation. <!-- Survey2026 -->

## File formats

Prefer open, widely supported formats that reduce technical barriers and improve long-term accessibility: <!-- Survey2026 --> <!-- ETAPS2025 -->

| Content type | Preferred formats |
|---|---|
| Text documents | TXT, Markdown (.md), PDF, HTML |
| Tabular data | CSV, TSV, JSON, YAML, XML |
| Code | Plain text source files |
| Images / figures | PNG, SVG |
| Archives | ZIP, TAR+GZIP (.tgz), TAR.BZIP2 (.tbz2) |
| Databases | SQLite, CSV dumps |

- Avoid sharing data exclusively inside PDFs or other formats that are difficult to parse and reuse. <!-- Survey2026 -->
- Separate reusable results (e.g., tables, data behind figures) into plain-text files. <!-- Survey2026 -->
- Avoid formats that require proprietary software for inspection. <!-- BeyerWinter2025 -->
- Prefer formats that are easy to read, parse, and reuse. <!-- BeyerWinter2025 -->

## Self-containment

> **Key principle:** Artifacts should be as self-contained as possible. Execution should not require downloads from external services during runtime. <!-- Survey2026 --> <!-- ETAPS2025 --> <!-- ZimmermannEtAl2023 -->

 <!-- Survey2026 -->
- **Complete:** include all components relevant to the paper. When proprietary components cannot be included, document how to obtain them and provide proxy or replacement data where possible.
- **Minimal external dependencies:** if unavoidable, document them explicitly and reference them through stable archival sources.
- **Easy to execute:** reduce setup effort as much as possible. Long or complex setup procedures should be automated or packaged using containers or virtual environments.

## Archive integrity

Before releasing: <!-- BeyerWinter2025 --> <!-- Survey2026 -->

- Test that compressed archives can be extracted correctly on different operating systems.
- Avoid absolute paths in archives, as they may cause extraction failures on different systems.
- Verify that all files are intact and not corrupted after packaging.
- Perform a preview upload to the target repository to verify the final appearance of the artifact page before making it public.

> **Tip:** Provide checksums (e.g., SHA-256 hashes) for important files so users can verify the integrity of downloaded artifacts. <!-- AdarEtAl2017 --> <!-- SEFM2024 -->

<!-- SEFM2024- -->
```bash
sha256sum <file>                    # Linux
shasum -a 256 <file>                # macOS
CertUtil -hashfile <file> SHA256    # Windows
```

## Package types

The appropriate packaging format depends on the nature of the artifact:

- **Simple package:** for non-executable artifacts such as documents, datasets, protocols, or files accessible with common tools (e.g., PDF viewers, spreadsheet software). These artifacts can typically be distributed as compressed archives (e.g., ZIP or TAR.GZ) without requiring complex installation procedures. <!-- Survey2026 --> <!-- ICSA2025 -->

- **Installation package:** for software systems, tools, scripts, or executable workflows. These packages should include all necessary code, dependencies, configuration instructions, and example data required for installation and execution in the user's environment. When artifacts depend on complex or specialized environments, consider providing containers or virtual machines to simplify setup and improve reproducibility. <!-- Survey2026 --> <!-- NDSS2026 -->

# Choosing a license

> **Key principle:** Without a license, others are not legally permitted to reuse, modify, or redistribute your artifact, even if it is publicly accessible. Licensing should be considered early in the project, not only at publication time. <!-- Survey2026 -->

## Step 1: Distinguish software from non-software artifacts

Different license categories apply to different artifact types:

- **Software licenses**: for code, scripts, tools, and executable artifacts.
- **Content licenses**: for datasets, documentation, protocols, reports, and other non-software materials.

> **Warning:** Be careful not to use the wrong license type (e.g., applying MIT to a dataset).

## Step 2: Select an appropriate license

**For non-software artifacts (data, documentation, protocols):**

| License | Key characteristic |
|---|---|
| **CC0** | Public domain dedication; maximizes reuse with no restrictions. Suitable for datasets and metadata. |
| **CC BY** | Requires attribution; good default for most research artifacts. |
| **CC BY-SA** | Attribution and share-alike; derivatives must use the same license. |
| **CC BY-NC / CC BY-ND** | Restrict commercial use or derivatives; avoid when reproducibility and reuse are goals. |

Use CC0 or CC BY whenever reuse and reproducibility are primary goals. Avoid restrictive variants (NC, ND) that may hinder adoption and integration with other artifacts. <!-- Survey2026 -->

For more details about Creative Commons licenses: https://creativecommons.org/cc-licenses/

**For software artifacts:**

| License | Type | Key characteristic |
|---|---|---|
| **MIT** | Permissive | Simple, minimal restrictions; broad reuse allowed. |
| **Apache 2.0** | Permissive | Includes patent protection; good for research software. |
| **GPL v3** | Copyleft | Requires derivatives to remain open-source. |

Permissive licenses (MIT or Apache 2.0) are recommended unless you explicitly want to enforce that derivatives remain open. <!-- Survey2026 -->

For more details about the main software licenses: https://choosealicense.com/licenses/


**Quick decision guide:**

| Artifact type | Recommended license |
|---|---|
| Code and scripts | MIT or Apache 2.0 |
| Datasets | CC0 or CC BY |
| Documentation | CC BY |
| Mixed artifacts | Apply the appropriate license to each component |

## Step 3: Check compatibility and constraints

Before finalizing the license: <!-- Survey2026 -->

- **Ownership:** verify that you have the right to license the artifact. Institutional policies, funder requirements, and employer agreements may impose restrictions.
- **Dependencies:** verify compatibility with the licenses of any third-party tools, libraries, or datasets included in the artifact.
- **Publication venue:** some conferences and journals have specific licensing requirements. Check before submission.
- **Sensitive data:** licensing does not override ethical or legal restrictions on data sharing.
- **Industry artifacts:** artifacts from industry settings may require legal review (Intellectual Property scrutiny) before sharing.

## Step 4: Apply the license correctly

<!-- Survey2026 -- > <!-- ZimmermannEtAl2023 -->
- Include a `LICENSE` file in the repository root.
- If the artifact includes components with different licenses (e.g., code under MIT and data under CC BY), clearly state which license applies to each component.
- Include a copyright notice identifying the rights holder.
- For third-party materials, include required notices and verify that redistribution is permitted.

# Persistent identifiers and citation metadata

## PIDs and immutability at publication

> **Rule:** Use the PID, not a URL, when citing the artifact in the paper. URLs break; PIDs are stable. <!-- AdarEtAl2017 -->

Key practices at publication time: <!-- AdarEtAl2017 -->

- Assign a PID to the artifact when archiving it.
- Add a SHA-256 hash to the artifact metadata for additional integrity verification.
- Ensure the PID appears in both the text and the metadata of the associated paper.

> **Tip:** On Zenodo, a DOI can be reserved before the final publication of the artifact, allowing you to include it in the paper before the camera-ready deadline. <!-- RE2026 -->

## CITATION.cff  and AUTHORS file

Include a `CITATION.cff` file in the repository root. That is, a plain-text, human- and machine-readable file that specifies how the artifact should be cited. It allows citation managers and platforms (e.g., GitHub, Zenodo) to generate correct citations automatically. <!-- RE2026 --> <!-- Survey2026 -->

A `.cff` file can be created at the [CFF initializer website](https://citation-file-format.github.io/cff-initializer-javascript/#/).

Also include: <!-- Survey2026 -->

- An `AUTHORS` file listing all contributors with affiliations and contact information.
- A copy of the accepted paper in PDF format.

Artifacts should include self-descriptive metadata covering at minimum: <!-- AdarEtAl2017 -->
- Title
- Authors
- Version
- License
- Dependencies
- Execution requirements
- Related publication
- Keywords

## Citing the artifact in the paper

Cite the artifact the same way you would cite other scholarly references, using the PID, and place it in a dedicated Data Availability Statement. <!-- ConfPub -->

Example citation entry (Zenodo): <!-- ConfPub -->

```bibtex
@Misc{VasconcelosMadeiralSoares2026-artifacts,
  author       = {Ana Paula Vasconcelos and Fernanda Madeiral and Sergio Soares},
  title        = {Research Artifacts of "GAPS: A guide for better artifact
                  preparation and sharing"},
  howpublished = {Zenodo},
  year         = {2026},
  doi          = {10.5281/zenodo.03091985},
  version      = {final}
}
```

> **Rule:** Always use the PID for the specific version used to produce the results in the paper. Update preprints and supplementary materials with the PID once it becomes available. <!-- ConfPub --> <!-- Survey2026 -->

# Data Availability Statements

A Data Availability Statement (DAS) explains which data and materials supported the study, whether they are openly available or restricted, and how other researchers can access them. It should appear as a dedicated section in the paper, typically before the references. <!-- Researchdata2026 --> <!-- ConfPub -->

A good DAS should: <!-- Researchdata2026 -->

- Identify which datasets, scripts, and materials support the results.
- State where the data are stored, with PID or persistent URL.
- Explain how access can be obtained.
- Describe any restrictions on sharing.
- Avoid vague statements such as "data available upon request." Provide concrete access instructions instead.

## DAS examples for common scenarios

<!-- Researchdata2026 -->
| Scenario | Example DAS |
|---|---|
| Artifacts publicly available | The research artifacts supporting this study are available at [PID URL]. |
| Privately shared during review, to be released after acceptance | Manuscript reviewers can preview the artifacts at [PRIVATE URL]. After acceptance, artifacts will be released at [PID URL]. |
| Data with privacy restrictions | The dataset contains information that could compromise participant privacy and cannot be made openly available. Metadata and access request instructions are available at [PID URL]. |
| Restricted artifacts available upon request | Some artifacts cannot be shared openly due to [legal / ethical / confidentiality] restrictions. Access may be requested from [CONTACT / INSTITUTION], subject to applicable restrictions. |
| Artifacts available within the paper | Artifacts supporting the findings of this study are available within the paper and/or its supplementary materials. |
| No artifacts were generated | No research artifacts or datasets were generated during this study. |

> **Tip:** Different journals, conferences, and publishers may have specific DAS requirements. Always verify venue-specific policies before submission. <!-- Researchdata2026 -->

# Shadow repositories

When original raw data cannot be made publicly available, a shadow repository approach can help balance transparency with ethical and legal constraints. <!-- MendezEtAl2020 --> <!-- Survey2026 -->

A **shadow repository** is a restricted-access repository storing the original, non-anonymized data and materials, kept private and not shared publicly. In parallel, a **public repository** hosts the shareable version of the artifact, typically including anonymized, filtered, or transformed data along with full documentation.

When using a shadow repository: <!-- Survey2026 -->

- Clearly document the relationship between the private and public versions.
- Describe what transformations were applied to the data and why.
- Explain why certain elements were removed or modified.
- Provide instructions for requesting access to the restricted repository when applicable.

# Transparency for restricted or processed data

> **Key principle:** Partial transparency is always more useful than no documentation at all. Even when data cannot be fully shared, artifacts should remain as transparent as possible. <!-- IPDPS26 --> <!-- BeyerWinter2025 -->

When full sharing is not possible: <!-- Survey2026 --> <!-- IPDPS26 -->

- Clearly indicate whether data are original (raw) or processed.
- Provide rich metadata and detailed dataset descriptions.
- Document all transformations applied (e.g., anonymization, filtering, aggregation).
- Explain the differences between the original and the shared version.
- Provide alternative datasets, synthetic data, or proxy data that allow artifact assessment independently of restricted materials. <!-- ICSA2025 -->
- Provide study protocols, coding schemes, and coding rules when raw qualitative data cannot be shared. <!-- Survey2026 -->
- Define a clear process for controlled data access, including criteria and instructions for submitting access requests. <!-- Survey2026 -->

When a component cannot be disclosed, state this explicitly rather than leaving it implicit: <!-- IPDPS26 -->

- *"Source code not available due to proprietary restrictions."*
- *"Dataset cannot be publicly shared due to licensing constraints."*

# Consent and ethical considerations at publication time

Before releasing an artifact publicly, revisit consent agreements and ethical constraints established during the research design phase. <!-- SaundersKitzingerKitzinger2015 --> <!-- Survey2026 -->

- Obtain explicit permission from participants before publishing any data. <!-- Survey2026 -->
- Clearly communicate what will be shared and how it will be used. <!-- Survey2026 -->
- Do not assume that anonymization alone is sufficient without proper consent agreements. <!-- Survey2026 -->
- Recognize that anonymization risks may evolve: even carefully anonymized data may become re-identifiable as participants publicly share related stories or social media content after publication. <!-- SaundersKitzingerKitzinger2015 -->
- When artifacts may perform risky operations or involve sensitive data handling, flag this explicitly in the README before the installation instructions. <!-- WOOT2025 -->

> **Warning:** Once datasets are publicly released and archived, removing them or fully undoing publication may be difficult or impossible. Verify anonymization, documentation, and licensing carefully **before** publishing. <!-- Graziotin2019 -->

Consent procedures may offer participants different levels of permission for data sharing: <!-- SaundersKitzingerKitzinger2015 -->

- Restricting access to the research team only.
- Allowing controlled research reuse.
- Permitting archival in repositories.
- Authorizing public dissemination of specific excerpts or media.

# Publishing visibility

Publishing is not the final step. Making the artifact visible increases its impact and encourages reuse. <!-- Survey2026 -->

In addition to linking the artifact in the paper: <!-- Survey2026 -->

- Share the PID in talks, social media, and academic mailing lists.
- Ensure the artifact is accessible independently of publisher paywalls.
- Provide sufficient documentation within the artifact so that users without full paper access can still understand and reuse it.

# Key takeaways

- Use dedicated archival repositories (e.g., Zenodo, FigShare, Dryad) for publication. GitHub and cloud storage are not archival solutions.
- The recommended workflow is: **develop on GitHub → archive on Zenodo → cite the DOI.**
- **Assign licenses explicitly.** Without a license, others cannot legally reuse your artifact.
- Use **permissive licenses** (MIT, Apache 2.0, CC BY) whenever reuse and reproducibility are goals.
- Include a `CITATION.cff` file, an `AUTHORS` file, and a `LICENSE` file in every artifact.
- Write a **Data Availability Statement** in the paper and cite the artifact with a PID.
- Use **version-specific PIDs** when citing artifacts associated with a paper. Once released, do not modify artifact contents, create a new version instead.
- **Partial transparency is always better than no transparency:** document what cannot be shared and why.
- Verify **consent, anonymization, and licensing** carefully before publishing. Reversing a public release is difficult or impossible.

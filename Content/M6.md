# Module 6 - Maintenance

Publishing an artifact is not the end of the process. Artifacts frequently become unusable within months of publication, due to dependency decay, deprecated libraries, broken links, unavailable services, or undocumented environment assumptions. Long-term usability requires active attention to preservation, environment isolation, dependency management, and stable archival practices. Sustainability also supports the cumulative nature of science: when artifacts remain usable, future researchers can reproduce earlier results, compare their work against prior baselines, and build incrementally upon existing research. <!-- BeyerWinter2025 --> <!-- Survey2026 -->

# Learning objectives

By the end of this module, you will be able to:

- Explain why research artifacts frequently become unusable shortly after publication.
- Identify the main causes of artifact decay and apply practices to prevent them.
- Design artifacts for long-term usability through durable formats, isolated environments, and stable dependencies.
- Manage artifact versions after publication using changelogs, tags, and immutability principles.
- Maintain artifacts actively after release through updates, issue management, and documentation upkeep.
- Prepare artifacts for extension and reuse beyond the original study.

# Artifact decay: causes and prevention

> **Key problem:** Artifact decay — sometimes called *bit rot* — refers to the gradual degradation of an artifact's usability over time, even when no changes are made to the artifact itself. Most decay is predictable and preventable. <!-- BeyerWinter2025 --> <!-- Survey2026 -->

## What causes artifacts to become unusable

| Cause | Description |
|---|---|
| **Dependency decay** | Libraries, packages, or tools used by the artifact are updated, deprecated, or removed. |
| **Broken links** | External datasets, APIs, or services referenced by the artifact become unavailable. |
| **Undocumented environment assumptions** | The artifact silently depends on specific OS versions, hardware configurations, or system settings that are no longer available. |
| **Platform incompatibility** | The artifact was only tested on a specific platform and fails on newer or different systems. |
| **Expired credentials or access** | APIs, private repositories, or institutional services required by the artifact become inaccessible. |
| **Format obsolescence** | Data or outputs were stored in proprietary or tool-specific formats that are no longer supported. |

## Prevention strategies

<!-- BeyerWinter2025 -- > <!-- Survey2026 -->
- **Pin dependency versions.** Specify exact versions of all libraries, tools, and dependencies. Floating or unspecified versions introduce unpredictability as upstream software evolves. <!-- BeyerWinter2025 -->
- **Use isolated environments.** Containers or virtual machines encapsulate dependencies and reduce the impact of changes in the host system over time.
- **Prefer open and widely supported formats.** Community-standard formats reduce maintenance effort and improve interoperability and reuse. Avoid obscure or tool-specific formats.
- **Avoid relying on external services.** APIs, remote databases, and third-party repositories may become unavailable. Include required data and dependencies within the artifact package or reference them through stable archival sources whenever possible.
- **Archive critical dependencies.** When external resources are essential, archive or mirror them alongside the artifact.
- **Prefer portable programming environments.** Tools and languages with large, stable communities (e.g., Python, R) are more likely to remain supported and executable over time.
- **Avoid self-hosting.** Personal or institutional websites are volatile. Use archival repositories that provide long-term preservation guarantees and persistent identifiers.

# Designing for long-term usability

## Durable file formats

> **Tip:** Choosing open, well-documented, and widely adopted file formats at the start of a project is one of the most effective ways to ensure long-term usability. <!-- BeyerWinter2025 --> <!-- Survey2026 -->

| Content type | Prefer | Avoid |
|---|---|---|
| Text and documentation | TXT, Markdown, PDF/A, HTML | Proprietary word processor formats |
| Tabular data | CSV, TSV, JSON | Excel-only formats, binary spreadsheets |
| Data interchange | JSON, XML, YAML | Proprietary binary formats |
| Images | PNG, SVG, TIFF | PSD, AI, tool-specific formats |
| Archives | ZIP, TAR.GZ | RAR, proprietary compression formats |
| Databases | SQLite, CSV dumps | Proprietary database exports |

When a specialized format is necessary (e.g., HDF5 for large datasets), prefer formats that are standard within the relevant research community and have stable, open-source readers available.

## Self-contained and isolated environments

Execution environments change over time. An artifact that depends on a specific combination of OS version, library versions, and system tools may become unusable as any of those components evolve. <!-- Survey2026 -->

<!-- Survey2026 -- > <!-- MendezEtAl2020 -->
- **Use containers (e.g., Docker).** Containers encapsulate the runtime environment together with the code, reducing sensitivity to changes in the host system. Ensure containers are fully self-contained and do not rely on external downloads during execution.
- **Use virtual machines.** VM images provide stronger isolation by including the OS. Distribute VMs in portable formats (e.g., OVA or OVF) for compatibility across hypervisors.
- **Use language-level environments.** For simpler artifacts, virtual environments (e.g., Python `venv`, conda, R `renv`) provide lighter isolation while still pinning dependency versions.
- **Include machine-readable environment specifications.** Files such as `requirements.txt`, `environment.yml`, `Dockerfile`, or `renv.lock` allow future users to reconstruct the environment even if the original container or VM is unavailable.

## Minimizing external dependencies

Every external dependency is a potential point of failure over time. Strategies to reduce this risk: <!-- Survey2026 --> <!-- BeyerWinter2025 -->

- Prefer open-source tools over proprietary or closed-source alternatives.
- Bundle required datasets and dependencies within the artifact package whenever possible.
- If external datasets or services are unavoidable, document their version, access URL, and expected availability, and consider archiving a local copy.
- Remove unused dependencies before release to reduce unnecessary maintenance burden.
- Clearly specify the platforms on which the artifact has been tested. Avoid overstating platform support.

## Long-term archival requirements

> **Key principle:** Long-term availability and immutability are both required. Artifacts must be hosted on platforms that commit to long-term preservation, and the content of a published version must not change after release. <!-- ConfPub -->

A repository suitable for long-term preservation should: <!-- ICSE2026 --> <!-- MODELS2025 --> <!-- ConfPub -->

- Host artifacts online with public access and no registration requirement.
- Provide a persistent identifier redirecting to an immutable URL.
- Have a declared long-term preservation policy.
- Support versioning while maintaining access to all previous versions.

> **Warning:** Avoid self-hosting and university repositories as the sole archival location. Institutional URLs may become unavailable over time as staff change or infrastructure is reorganized. Prefer established platforms such as Zenodo, FigShare, Dryad, or Software Heritage. <!-- Survey2026 -->

Additional archival requirements: <!-- Survey2026 --> <!-- BeyerWinter2025 -->

- Prefer repositories that allow anonymous access and do not require user registration, manual approval, or restrictive access controls to download the artifact.
- Avoid platforms that track user access (e.g., IP tracking) or require individual download permissions.
- Avoid financial, legal, or technical barriers that limit access to the artifact.
- Perform a preview upload to verify the final appearance of the artifact before publication.

> **Tip:** Update the preprint and artifact with the PID provided by the publisher once it becomes available. Do not submit the postprint. <!-- Survey2026 -->

# Versioning and changelogs

## Why post-publication versioning matters

Artifacts evolve after publication. Bugs are discovered, dependencies break, documentation is improved, and new use cases emerge. Maintaining clear version records helps users understand what changed, when, and why, and allows them to access the specific version referenced in any given publication. <!-- Graziotin2019 --> <!-- Survey2026 -->

## Lifecycle version management

Maintain a clear version history corresponding to the different phases of the research lifecycle. <!-- Survey2026 --> <!-- ConfPub -->

| Phase | Recommended action |
|---|---|
| During research | Develop on GitHub or similar; use branches and commits for traceability. |
| Before review | Create a stable tagged release; anonymize if required by the submission venue. |
| Camera-ready / publication | Archive on Zenodo or similar; obtain a permanent PID. |
| Post-publication | If changes are needed, create a new version rather than modifying the original. |

## Version-specific vs. concept PIDs

Platforms such as Zenodo and FigShare support two types of identifiers: <!-- USENIXSec2026 --> <!-- BeyerWinter2025 -->

- **Version-specific PIDs** point to a single, fixed version of the artifact. Use these in the paper to reference the exact version used to produce the reported results.
- **Concept PIDs** (version-agnostic) redirect to the latest version of the artifact. These are useful when the artifact may evolve during review, since the identifier remains valid without requiring updates to the paper link.

> **Rule:** When citing artifacts associated with a paper, prefer version-specific PIDs. Concept PIDs may later point to newer versions, which can compromise reproducibility. <!-- BeyerWinter2025 -->

> **Tip:** Provide a hash or commit identifier alongside the DOI to certify the exact artifact version used in the publication. When artifacts are not publicly archived, SHA-256 checksums can help identify the exact version associated with a study or review process. <!-- Survey2026 --> <!-- ConfPub -->

## Version tagging

Each published version should correspond to a clear, explicit version tag. Zenodo allows version tags to be added or edited even after publication. A useful tagging schema produces predictable, self-explanatory identifiers that can be cited directly in Data Availability Statements. <!-- ConfPub -->

Example tagging schema (based on OOPSLA 2025 practice): <!-- ConfPub -->

```
VENUE-YEAR-submission          # version accompanying the submitted paper
VENUE-YEAR-camera-ready        # version accompanying the final paper
VENUE-YEAR-AEC-submission      # version submitted to artifact evaluation
VENUE-YEAR-AEC-revision        # version after kick-the-tires feedback
VENUE-YEAR-AEC-final           # version after addressing reviewer comments
```

If you later publish a new version, Zenodo will show a banner indicating a newer version is available, but the various versions will be cleanly separated using the tags. Authors can cite the submission version explicitly in the Data Availability Statement and also reference the latest version via its concept PID.

> **Tip:** It is useful to separate a fixed archival artifact used for reproducibility (e.g., Zenodo) from an actively maintained development repository intended for continued updates and reuse (e.g., GitHub). <!-- ConfPub -->

## Changelog

A changelog documents what changed between versions and helps users quickly understand whether an update affects their use of the artifact.

A changelog should: <!-- Survey2026 -->

- List changes by version, in reverse chronological order (newest first).
- For each version, note the date and a description of changes.
- Distinguish between changes that affect reproducibility (e.g., bug fixes that change outputs) and those that do not (e.g., documentation improvements).

Example changelog structure:

```
# [2.0.0] - 2026-05-01
## Changed
- Updated Python dependency from 3.9 to 3.11.
- Replaced deprecated matplotlib API calls.

# [1.1.0] - 2025-11-15
## Fixed
- Corrected data cleaning script that produced incorrect output for edge cases.
## Added
- Minimal working example for quick validation.

# [1.0.0] - 2025-08-20
- Initial release accompanying the paper submission.
```

## Immutability of published versions

> **Rule:** Once an artifact version is associated with a publication, its contents must remain immutable. Instead of modifying a released version, create a new versioned release. Some PIDs technically allow the objects they identify to change, do not use that feature. Immutability of the content pointed to by a PID is a hard requirement for reliable scientific reference. <!-- AdarEtAl2017 --> <!-- ConfPub -->

- Preserve reproducibility and traceability for all users who previously accessed the original. <!-- AdarEtAl2017 -->
- When using remote repositories during submission, create a stable tagged release specifically for the published artifact. Avoid linking users to actively changing development branches. <!-- BarowyEtAl2023 -->
- Add a SHA-256 hash to the artifact metadata for additional integrity verification. <!-- AdarEtAl2017 -->

# Active maintenance after publication

> **Key principle:** Sustainability involves actively supporting users who interact with the artifact after publication, not only preventing decay. <!-- Survey2026 -->

## Maintaining usability over time

- **Monitor and respond to issues.** A responsive GitHub Issues page or discussion forum helps users report problems and receive assistance, and creates a public record of known issues and resolutions for future users. <!-- Survey2026 -->
- **Update dependencies when feasible.** When dependencies release breaking changes or security updates, updating the artifact preserves its usability. Shared responsibility between collaborators helps keep artifacts current. <!-- Survey2026 -->
- **Document known issues and expected failures.** If certain problems are known but unresolved, document them explicitly in the README. If a compared tool crashes on a subset of inputs, note this as expected behavior, do not leave critical limitations undocumented. <!-- Survey2026 -->
- **Never silently modify published versions.** If a correction is necessary, create a new version with a changelog entry explaining what was changed and why. <!-- Survey2026 -->

## Keeping documentation current

After each update, review and update: <!-- Survey2026 -->

- The README for accuracy.
- Execution instructions if commands or dependencies changed.
- System requirements if environment assumptions changed.
- All links and references to verify they are still active.

A well-maintained artifact should include: <!-- Survey2026 -->

- A contributing guide explaining how others can contribute improvements.
- A changelog documenting the evolution of the artifact.
- A `CITATION.cff` file that remains current.
- Contact information that remains valid over time.

> **Tip:** Institutional email addresses may not remain valid long-term. Consider providing your ORCID, a persistent professional profile, a project website, or a lab email as alternative contact.

# Supporting extension and reuse

> **Key principle:** Well-prepared artifacts are not only reproducible, they are also extensible. Supporting reuse beyond the original study increases the long-term scientific impact of the work. <!-- Survey2026 --> <!-- BeyerWinter2025 -->

## Designing for extensibility

- **Include source code.** A tool artifact that includes its source code, all non-standard requirements, and a working description of how to compile it enables others to extend and adapt it. <!-- Survey2026 -->
- **Provide a Reusability Guide.** Document explicitly which parts of the artifact are intended for reuse, how to adapt it to new inputs or use cases, and any known limitations on reusability. <!-- Survey2026 -->
- **Describe extension scenarios.** Documentation should describe plausible scenarios for how the artifact could be extended. Providing a worked example of an extension is a plus. <!-- Survey2026 -->
- **Document how to adapt to new inputs.** Explain which parameters, datasets, or configurations need to change for the artifact to be applied to a new study or dataset. <!-- Survey2026 -->
- **Explicitly identify which parts are reusable.** Not all parts of an artifact need to be designed for reuse. What matters is being explicit about which parts are reusable and which are not. <!-- Survey2026 -->

## Enabling community reuse

<!-- Survey2026 -- > <!-- BeyerWinter2025 -->
- Use open licenses that explicitly allow reuse, modification, and redistribution.
- Structure code as modular components whenever possible, making it easier for others to import and build upon individual parts.
- Use public benchmarks and datasets that others can also access, enabling comparison and extension across studies.
- Structure and document datasets so they can be reused across multiple studies, not only for the paper they originally supported.
- Avoid relying on unstable external resources. If external datasets, APIs, or repositories are required, document versioning and long-term availability expectations, and archive critical dependencies whenever possible.

# Key takeaways

- Artifact decay is common and predictable. Most decay is preventable through careful decisions made before publication.
- **Pin dependency versions, use isolated environments, prefer open formats, and avoid relying on external services.**
- Prefer archival repositories with explicit long-term preservation policies. **Immutability and persistence are both required.**
- Use **version-specific PIDs** when citing artifacts in papers. Never silently modify a published version. When necessary, create a new one and document what changed.
- Maintain a **changelog** and use explicit **version tags** so the artifact history is transparent and citable.
- Respond to issues, update dependencies when feasible, and keep documentation current after publication.
- Provide a **Reusability Guide** and extension scenarios to support uses of the artifact beyond the original study.

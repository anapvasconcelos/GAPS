# Module 3 - Documentation

Good documentation is one of the most important factors in artifact adoption. Without it, even well-structured and technically sound artifacts may remain unusable. Research artifacts are not only technical deliverables, they are communication mechanisms. Well-documented artifacts help others understand the study design, execution workflow, assumptions, limitations, and expected outputs without requiring direct contact with the authors. <!-- WilsonEtAl2017 --> <!-- Survey2026 -->

In practice, documentation is often treated as an afterthought. This results in incomplete instructions, missing context, and artifacts that are difficult or impossible to reuse. Preparing documentation incrementally throughout the research process, starting with a brief explanatory comment at the beginning of each script, significantly reduces this problem. <!-- WilsonEtAl2017 --> <!-- Survey2026 -->

# Learning objectives

By the end of this module, you will be able to:

- Explain why documentation is essential for artifact usability, reproducibility, and reuse.
- Identify the levels of artifact documentation and what each should cover.
- Write an effective README file with all required sections.
- Document repository structure, naming conventions, and key components clearly.
- Map artifact contents and outputs to the claims, figures, and results reported in a publication.
- Communicate artifact limitations, scope, and non-shared components transparently.
- Apply complementary documentation practices to improve artifact usability.

# Levels of artifact documentation

Good artifact documentation operates at three complementary levels. All three are necessary, because an artifact that is well-organized but lacks execution instructions is unusable; one with step-by-step instructions but no connection to the paper cannot be independently validated; one that reproduces results but provides no structural overview is difficult to inspect and extend. <!-- Survey2026 -->

| Level | Purpose | Key questions answered |
|---|---|---|
| **Operational** | Explains how to install, execute, and validate the artifact. | - How do I run this?<br> - What do I need?<br> - What output should I expect? |
| **Structural** | Describes how the artifact is organized. | - Where is everything?<br> - What does each folder and file contain? |
| **Scientific** | Explains how the artifact connects to the research and the paper. | - Which claims does this support?<br> - How do outputs relate to the paper? |

# Operational documentation

> **Key principle:** Write operational documentation clearly enough that someone with reasonable technical knowledge can install, execute, and validate the artifact without background knowledge about the study. <!-- Survey2026 -->

## Assumed background and requirements

State the expected technical background of the user at the beginning. Document all technical requirements: <!-- Survey2026 --> <!-- ICSE2026 --> <!-- ETAPS2025 -->

- Operating system and version.
- Hardware requirements: CPU, GPU, memory, disk space, and any specialized peripherals.
- All software dependencies and their exact versions.
- Estimated execution time and storage requirements.
- Any passwords, access credentials, or software licenses needed.

> **Tip:** Avoid overstating platform support. Clearly state which platforms have been tested and avoid claiming compatibility that has not been verified. Document hardware architecture assumptions (e.g., x86, ARM) explicitly. Architecture incompatibilities may prevent reproduction even when all software dependencies are available. <!-- Survey2026 --> <!-- ETAPS2025 -->

If the artifact requires specialized hardware, provide instructions for how users can gain access to those resources. <!-- Survey2026 --> <!-- ETAPS2025 -->

## Step-by-step execution instructions

Provide complete, step-by-step instructions for: <!-- Survey2026 -->

- Obtaining and unpacking the artifact.
- Preparing the environment and installing dependencies.
- Executing experiments or analyses.
- Interpreting and locating outputs.
- Extending or uninstalling the artifact, when applicable.

All commands must be listed explicitly and formatted for copy-paste into a terminal. For each command, specify: <!-- Survey2026 --> <!-- Padhye2019 -->

- Which directory to run it from.
- What output files it generates and where they are located.
- Whether it creates new directories, accesses the internet, or uses significant disk space.
- What output to expect if execution is successful.

> **Tip:** Write the documentation as if you are a stranger to your own work. Do not assume users share your context, tools, or environment. <!-- Survey2026 -->

## Execution time and resource expectations

Document how long each major step takes on reference hardware. <!-- Survey2026 --> <!-- ICSA2025 -->

- If the full run takes more than one hour, provide a shorter representative subset that allows users to verify core functionality first.
- For long-running experiments, provide reduced input datasets or pre-computed intermediate results. <!-- Survey2026 --> <!-- Padhye2019 -->
- Individual steps should not take longer than 8–12 hours to execute. <!-- Survey2026 -->
- Include progress messages or estimated duration for each execution step. <!-- Survey2026 -->
- When experiments run for multiple days, provide reduced inputs, allow partial reproduction, or consider providing a screencast as an alternative. <!-- Survey2026 -->

Informing users about approximate running times helps them distinguish normal execution from failures and reduces uncertainty during reproduction attempts. <!-- BarowyEtAl2023 -->

## Idempotency and error recovery

- Make each step idempotent whenever possible. Re-running the same command should produce the same result regardless of how many times it is executed. <!-- Padhye2019 -->
- Document expected failures and known tool limitations explicitly. If the artifact produces specific error messages or warnings that are expected and safe to ignore, state this clearly. <!-- Survey2026 -->
- Help users identify failing steps quickly. <!-- Padhye2019 -->
  - Cascading errors, where one undocumented failure causes later steps to fail silently, are among the most frustrating experiences for artifact users. <!-- Padhye2019 -->

# Structural documentation

> **Key principle:** Structural documentation describes how the artifact is organized, making it possible for users to navigate the repository efficiently without having to read the entire paper first. <!-- Survey2026 -->

## Folder structure

A documentation block describing the folder structure should appear in the main README. Example: <!-- MendezEtAl2020 --> <!-- Survey2026 -->

```
project/
├── data-raw/         # Original, unmodified collected data
├── data-clean/       # Processed datasets derived from raw data
├── scripts/          # Data collection, cleaning, and analysis scripts
├── figures/          # Generated plots and visualizations
├── docs/             # Supplementary documentation and protocols
└── README.md         # Repository overview and usage instructions
```

For each directory, describe: <!-- Survey2026 --> <!-- ETAPS2025 -->
- Its purpose and the types of files it contains.
- The purpose of each major directory and the role of key files within it.
  - Whether its contents are essential or auxiliary.
  - Which files are required to execute or reproduce the artifact.
- Where raw and processed data are stored.
- Where scripts, execution entry points, and generated results are located.
  - The relationships between scripts and outputs.

Provide a table of contents or navigation index in the README when the repository is large or complex. <!-- Survey2026 -->

## In-folder documentation

For complex projects, place additional documentation files within specific folders rather than concentrating all explanations in the root README. A brief description of data organization inside the `data-raw/` or `data-clean/` folder, or usage notes inside the `scripts/` folder, reduces the cognitive load required to navigate the artifact and helps users locate relevant context close to the files it describes. <!-- ETAPS2025 --> <!-- Survey2026 -->

A well-organized README should include: <!-- ETAPS2025 --> <!-- Survey2026 -->

- A concise project summary.
- Descriptions of important files and directories.
- Explanations of data organization.
- Guidance on how the artifact should be interpreted or reused.

> **Tip:** Deliberately include operational details that may seem trivial to the original authors but are essential for external users. <!-- ETAPS2025 --> <!-- Survey2026 -->

## Naming conventions

From a documentation perspective, the critical practice is to **align file and folder names with the terminology used in the paper**. Variable names, dataset labels, script names, and output files should map directly to the publication. When terminology changed between artifact development and paper submission, include a brief explanation of old versus new terminology in the README before the execution instructions. <!-- Survey2026 --> <!-- MendezEtAl2020 -->

Naming conventions were introduced in [Module 2 - Preparation](content/M2.md).

## Distinguishing essential from auxiliary components

Clearly distinguish which components are required for execution or reproduction and which are supplementary or optional. Explicit labeling helps users prioritize attention and troubleshoot more effectively. <!-- Survey2026 --> <!-- ETAPS2025 -->

# Scientific documentation

> **Key principle:** Scientific documentation explains how the artifact connects to the research study and the published paper, allowing reviewers and future researchers to understand which claims are supported, how outputs were produced, and how results relate to the paper. <!-- Survey2026 -->

## Artifact purpose statement

Begin with a clear explanation of what the artifact is, what it does, and how it supports the paper. Go beyond "this is a replication package of..." and explain why the artifact matters and what it enables. <!-- ICSE2026 --> <!-- Survey2026 -->

The purpose statement should: <!-- Survey2026 -->

- Briefly describe the study goal and the role of the artifact.
- List the main components included.
- Explicitly state which claims in the paper are supported by the artifact and how.
- Explain why certain claims may not be supported, if applicable.

## Data description

When the artifact includes datasets, document: <!-- Survey2026 --> <!-- ETAPS2025 -->

- The meaning of each variable, feature, or field.
- How the data were collected and why.
- Preprocessing and cleaning procedures applied.
- Inclusion and exclusion criteria.
- Storage requirements.
- Any ethical, legal, or licensing constraints associated with the data.

For non-executable artifacts (interview guides, protocols, codebooks, qualitative datasets), also explain how the materials can be interpreted and reused by other researchers or practitioners. <!-- RE2026 --> <!-- Survey2026 -->

## Mapping outputs to paper results

> **Rule:** Do not ask users to run scripts without explaining what to expect. Provide an explicit mapping between artifact outputs and paper results. <!-- Padhye2019 -->

For each relevant output, specify: <!-- Survey2026 -->

- Which figure, table, subsection, or claim in the paper it corresponds to.
- Where the output file is located within the repository.
- How to interpret the output relative to the paper.
- How long it takes to generate.

A simple mapping table is often the clearest approach: <!-- Rapoport -->

| Paper element | Location in the paper | Artifact file |
|---|---|---|
| Figure 3 | Section 4 | `scripts/fig3.py` |
| RQ2 analysis | Section 5 | `analysis/stats.R` |
| Survey data | Page 7 | `data/survey.csv` |

For claims not supported by the artifact, explain why they are omitted. Organize the list by section and subsection of the paper. <!-- Survey2026 -->

Example validation block: <!-- Padhye2019 -->

```
Validate results (30 human-minutes + 5 compute-minutes)

Supported claims:
- Table 1: results/tab1.csv reproduces Table 1 on Page 5.
- Figure 2: results/plot2.pdf reproduces Figure 2 on Page 8.
- Page 7, para 3: "We outperform the baseline by 2x."
  - See results/comparison.csv — the second column (our system) should be approximately twice the third column (baseline).

Claims not supported by this artifact:
- The claim on Page 8 requires specialized hardware not available in this package and is therefore out of scope.
```

> **Note:** The paper should remain understandable without requiring readers to inspect the artifact. Artifact documentation complements the paper by supporting execution, inspection, and reuse — it should not serve as a container for unrelated scientific content. <!-- IPDPS26 -->

# How to write an effective README

> **Key principle:** The README is the primary entry point for anyone working with the artifact. It should be clear, complete, and honest, allowing users to understand what the artifact does, how to use it, and what to expect without needing to contact the authors. <!-- ZimmermannEtAl2023 --> <!-- Survey2026 -->

## Required sections

**Summary of artifacts.** Describe what the artifact is and why it exists. Communicate the artifact's value and purpose beyond "This is a replication package for...". <!-- ICSE2026 --> <!-- Survey2026 -->

**Artifact description.** Provide a structured overview:  <!-- ICSE2026 --> <!-- Survey2026 -->
- An introduction explaining the overall objective.
- An overview of the main components and what each does.
- A description of the folder structure, including the purpose of each folder and key files.
- A description of what is included and what is not, with reasons for any omissions.
- Data provenance and ethical or legal statements, when applicable.

> **Tip:** Think of this section as the explanation you would give to a new researcher about to continue the work. <!-- Survey2026 -->

**System requirements.** Clearly state what is needed to run the artifact: <!-- ICSE2026 --> <!-- Survey2026 --> <!-- ETAPS2025 -->
- Expected technical background of the user.
- Operating system and version.
- Hardware requirements.
- All software dependencies and their versions.
- Estimated execution time per major step.
- Total storage requirements.

**Potential risks.** If the artifact performs potentially risky operations (privileged execution, network access, large file creation, sensitive data handling), flag these clearly at the top of the README, before the installation instructions. For each command, clarify whether it: <!-- WOOT2025 --> <!-- Survey2026 --> <!-- Padhye2019 -->
- Creates or modifies files.
- Accesses the internet.
- Uses significant disk space.
- Requires elevated permissions.

**Getting started guide.** Provide a lightweight setup and validation procedure completable in approximately 60 minutes. This guide should:  <!-- Survey2026 --> <!-- BarowyEtAl2023 -->
- List all installation steps.
- Include a minimal working example that confirms the artifact is correctly installed and functioning.
- Describe what output to expect when everything is working correctly.
- Include a basic smoke test that verifies core functionality.

**Step-by-step instructions.** Provide complete instructions for reproducing the results presented in the paper: <!-- Survey2026 -->
- List all commands required, copy-paste ready.
- Specify which directory each command should be run from.
- Document which output files each command generates and where they are located.
- Indicate approximate execution time for each step.
- Note expected warnings or error messages that can be safely ignored.
- Include sample outputs or logs for comparison, stored in a separate folder so they are not overwritten during testing.
- Provide instructions for how to gain access to specialized hardware when required.

**Troubleshooting.** <!-- Survey2026 -->
- Include common installation and runtime errors with solutions.
- Known issues and limitations.
- Frequently asked questions
- A link to a GitHub Issues page or support forum, when available.

> **Tip:** Being transparent about problems is more helpful than presenting the artifact as flawless. Users appreciate knowing upfront if something has only been tested on specific machines or has known edge cases. <!-- Survey2026 -->

**Reusability guide.** <!-- Survey2026 -->
- Explain which parts of the artifact can be reused and how.
- Identify which components are intended for reuse and which exist only to reproduce the paper results.
- Describe limitations on reusability.
- Provide example extension scenarios when possible.

> **Note:** Not all parts of an artifact need to be prepared for reusability. A script that generates a specific figure may only be intended for reproduction. What matters is being explicit about which parts are reusable and how. <!-- Survey2026 -->

**Licenses.** State the licenses that apply to the artifact. <!-- ZimmermannEtAl2023 --> <!-- Survey2026 -->
- Include which license applies to each component when different licenses are involved.
- Include the full text in a dedicated `LICENSE` file.
- Include a copyright notice identifying the rights holder.

**Citation.** Provide citation information for the artifact and the associated paper: <!-- Survey2026 --> <!-- RE2026 -->
- Full citation of the associated paper (with PID).
- The PID or archival link to the artifact.
- An `AUTHORS` file listing all contributors.
- A `CITATION.cff` file.
  - A plain-text, human- and machine-readable file containing citation metadata that can be automatically processed by platforms (such as GitHub) to generate citation information.
  - Create one at the [CFF website](https://citation-file-format.github.io/cff-initializer-javascript/#/).

**Authors and contact.** List all authors with institutional affiliations and contact information. Note that institutional email addresses may not remain valid long-term. Consider providing additional means of contact. <!-- MongomeryEtAl2024- -->

# Documenting limitations and non-shared components

> **Key principle:** Transparency about what the artifact does not include is as important as describing what it does. Missing or unexplained omissions erode trust and make independent validation harder. <!-- Survey2026 --> <!-- IPDPS26 -->

## Scope and unsupported claims

An artifact does not need to support every claim in the paper, but unsupported claims must be clearly justified. For each claim in the paper: <!-- Survey2026 -->

- State whether it is supported by the artifact.
- For supported claims, explain how the artifact provides that support.
- For unsupported claims, explain why they are omitted (e.g., proprietary data, specialized hardware, ethical constraints, excessive computation time).

> **Tip:** Explicitly listing all claims helps distinguish bugs that invalidate the paper's results from bugs that are simply a normal part of the software engineering process. <!-- Survey2026 -->

Claims about reproducibility, applicability, automation, scalability, or platform support should reflect the actual conditions under which the artifact was evaluated. Overly broad claims are problematic when based on a limited subset. <!-- ACMSIGPLAN -->

## Non-shared components

When components cannot be disclosed due to legal, contractual, ethical, or proprietary restrictions, document this explicitly rather than leaving it implicit. <!-- IPDPS26 --> <!-- Survey2026 -->

Examples of disclosure statements: <!-- IPDPS26 -->

- *"Source code not available due to proprietary restrictions."*
- *"Dataset cannot be publicly shared due to licensing constraints."*
- *"Raw interview transcripts are not included due to participant privacy. The coding schema and study protocol are provided instead."*

When components are restricted, share as much as possible through alternatives: <!-- Survey2026 --> <!-- ICSA2025 -->

- Study protocols, coding schemes, and coding rules.
- Anonymized, synthetic, or aggregated datasets.
- Intermediate analysis artifacts that explain how conclusions were derived.
- Artificial replacement data that allows artifact assessment independently of the restricted materials.

> **Tip:** Providing partial transparency is always more useful than providing no documentation at all. <!-- BeyerWinter2025 -->

> **Tip:** When the paper has no artifacts at all, explain in the paper itself why no artifact is provided, given the broad range of materials that can constitute an artifact. <!-- IPDPS26 --> <!-- Survey2026 -->

## Impact of anonymization on interpretability

When data have been anonymized before sharing, document the impact on the data's interpretability. Explain how anonymization may reduce clarity or completeness, and indicate any limitations this introduces for reproduction or reuse. <!-- SaundersKitzingerKitzinger2015 --> <!-- Survey2026 -->

## Contextual variability in empirical studies

In studies involving human participants, exact reproducibility may not be achievable. Artifacts should: <!-- Survey2026 -->

- Document the experimental context clearly.
- Support replication of procedures rather than exact results.
- Explain how results may vary across different contexts or participant populations.

## Controlled data access

When data cannot be made fully public but can be made available under controlled conditions: <!-- Survey2026 -->

- Describe the nature of the data and the constraints that prevent full public sharing.
- Define the criteria for granting access.
- Provide clear instructions for submitting an access request.
- Indicate any governance mechanisms in place (e.g., a Data Use Agreement Committee).


# Complementary documentation

Beyond the README, additional forms of documentation can significantly improve artifact usability. <!-- Survey2026 -->

**Inline comments and code documentation.** Comment scripts and code, especially at complex or non-obvious steps. When a paper introduces specific algorithms, heuristics, or implementation strategies, explicitly indicate where these components are implemented in the source code. <!-- BarowyEtAl2023 --> <!-- Survey2026 -->

**Literate programming and notebooks.** R Markdown and Jupyter notebooks, for instance, combine executable code with explanatory text, making the connection between analysis steps and results visible in a single document. <!-- Survey2026 -->

**Tutorials and demonstration videos.** Consider providing a short demonstration video or screencast to illustrate how the artifact works and highlight its main features. Tutorial-style videos are particularly useful when: <!-- ASE2025 --> <!-- Survey2026 -->

- The installation or execution workflow is involved.
- The artifact includes a graphical interface.
- Understanding outputs requires context that is difficult to convey in text alone.

**Additional visual materials.** Architectural diagrams, screenshots, and annotated figures help users understand the artifact structure, expected outputs, and system components. <!-- Survey2026 -->

**Documenting differences from the paper.** Any relevant differences between the artifact and the published paper should be documented explicitly. Examples include: <!-- BarowyEtAl2023 --> <!-- Padhye2019 -->

- Bug fixes introduced after submission.
- Updated or modified scripts.
- Datasets modified to remove confidential information.
- Reduced workloads provided for reproducibility purposes.
- Changes in terminology.

> **Tip:** When terminology differs between the artifact and the paper, include a brief explanation of old versus new terminology in the README. <!-- Padhye2019 -->

# Key takeaways

- Documentation operates at three levels: **operational, structural, and scientific**. All three are necessary.
- The **README is the primary entry point.** Write it as if you are a stranger to your own work.
- **Map outputs explicitly** to figures, tables, and claims in the paper.
- **Document what is not included and why**, with clear justifications.
- **Partial transparency is always better** than no documentation.
- Complementary materials (such as )inline comments, screencasts, diagrams, and notebooks) improve usability and adoption considerably.
- **Be honest about limitations, known issues, and variability.**
